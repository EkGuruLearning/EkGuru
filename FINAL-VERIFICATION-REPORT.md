## 1. WhatsApp column position — the discrepancy was real, and the report was wrong

`whatsapp` is the **22nd name in `EKGURU_APPLICATION_HEADER`** (1-based, of 69). Its
**physical spreadsheet column depends on what the tab looked like when migration ran**:

| Tab state at migration | Columns appended | Physical column of `whatsapp` |
|---|---|---|
| Legacy 17-column tab | 52 (all of 18–69, in schema order) | **22** |
| Already at 2.0.0's 68 columns (**the realistic production case**) | 1 (`whatsapp` only) | **69** |

So the implementation report's unqualified "`whatsapp` is **column 22**" is true only for
a fresh legacy migration. §5 and §10 of `FINAL-IMPLEMENTATION-REPORT.md` have been
corrected.

**Proof that the absolute number does not matter** — writes are header-driven
(`map[column]`), never positional:

- 19/19 checks pass in both migration scenarios.
- Scenario B (2.0.0 tab): 1 column appended, all 68 headers unmoved, the pre-existing row
  is **byte-identical**, its `whatsapp` cell stays `""`, the new row's number lands in
  physical column 69, and physical column 22 is still `subjects_json`.
- Dragging `whatsapp` to **physical column 1** still puts `+919876543210` in the right
  cell — nothing in `ApplicationIntake.gs` hardcodes 22 or 69.
- An unknown payload key never creates a column; it is kept in `details_json`.

**Final column count: 69.** Legacy 17 first, unchanged, in place. Migration is
append-only, pads new cells with `""`, and a second run is a no-op (re-verified).

## 3. Submission idempotency

**Functions:** `newSubmissionId(kind)` / `clearSubmissionId(kind)` in `js/intake.js`
(sessionStorage key `ekguru-intake-id-<kind>`); the id is sent as `submission_id` in the
POST body; `ekFindSubmission_(tab, map, submissionId)` in `ApplicationIntake.gs` scans
`details_json` for an exact match and `ekSubmitApplication_` routes a hit to
`ekUpdateExisting_` instead of appending. Format: `application-<base36 time>-<random>`.

| Requirement | Result |
|---|---|
| Browser generates and keeps a stable id | ✅ two failed attempts carried the **same** id; the eventual success used it too |
| `js/intake.js` sends it | ✅ `submission_id` present on every POST, format-validated |
| Backend validates and uses it | ✅ stored in `details_json`; used for dedupe |
| Retrying creates no second row | ✅ 3 identical retries → **1 row, 1 email**, same `EG-` reference, `duplicate: true` on retries, `mail: "skipped"` |
| A new application gets a new id | ✅ the id is cleared only after `j.ok && j.reference`; a later submission minted `application-…` ≠ the first |
| Two simultaneous identical submissions do not duplicate | ✅ see below |

**The race.** The whole submit path runs under `LockService.tryLock(25000)` and releases
in a `finally`. A submission that cannot take the lock is **refused** ("busy, try again"),
not written — verified by holding the lock and posting: `ok:false`, zero rows, zero
emails. Two identical posts arriving serially (the realistic outcome of a double-tap)
end as **one row, one email, one reference**. Two *different* ids for the *same person*
also collapse to one row, matched by recent email and reported as an update.

⚠️ Honest limit: a true simultaneous race cannot be executed in this environment (no
script runner, `tryLock` is mocked). The evidence is the lock's structure plus the
serialised outcome, not an observed parallel interleaving.

## 4. Resubmission preservation

Method: build one row with **every optional filled**, have an admin set
`status = needs_information` and write a private `review_notes`, then post a small second
payload shaped like the real form (all 7 required answers + 3 changed values).

| Requirement | Result |
|---|---|
| Changed fields update | ✅ `name`, `city`, `rate_usd` all updated |
| Omitted optionals unchanged | ✅ **43 of 43** columns byte-identical |
| Status unchanged | ✅ stays as set; from `needs_information` it advances to `under_review` and records `previous_status` (documented behaviour) — **an approved row stays approved** (verified separately) |
| Reviewer notes unchanged | ✅ `review_notes`, `reviewed_by` intact |
| No private information lost | ✅ `email, whatsapp, review_notes, reviewed_by, rejection_reason, consent_* , doc_refs` all unchanged; `details_json` only gains the new `submission_id`, every overflow value survives |

Mechanism, verified by name: `values.__supplied[f.src]` records what this payload
actually contained; `ekUpdateExisting_` skips any field present now, and never copies an
empty prior value back over a fresh one; `details_json` is key-merged; `keep[]` protects
`reference, status, approved, review_notes, rejection_reason, reviewed_by, reviewed_at,
previous_status, email_status, email_sent_at, created_at, timestamp`.

Also verified: **absent ≠ empty**. An optional left out is kept; an optional *sent empty*
is cleared (deliberate); a *required* answer sent empty is refused, so a tutor cannot
blank their bio. A resubmission addressed by `reference` alone behaves identically.

### DEF-1, proved end to end (19/19)

The risk was never in the backend — it was in what the browser sent. So the proof goes
through the real form into the real backend:

1. A tutor fills only the seven required answers and submits → the payload **omits** all
   three selects, and the server applies its documented defaults (`50 min`, `USD`).
2. They then choose **90 min / INR / Fluent** and resubmit → stored.
3. They come back later, change **only their city**, and never touch those selects (a
   fresh page load puts them back on `Select`) → the payload omits them again, and the
   stored `90 min`, `INR` and `Fluent` **survive**. Before the fix this step sent
